🏗️ Infrastructure
Terraform-managed Azure and Databricks infrastructure — declarative, reproducible, and governed
Infrastructure-as-Code First All MRx infrastructure is defined, versioned, and deployed exclusively via Terraform. No manual Azure portal changes are permitted in staging or production environments. Every resource is created from code, ensuring full reproducibility and auditability of the platform state.
🌍
Terraform Deployments
  • Terraform Cloud / Enterprise — remote state management with team-based access controls
  • Modular architecture: reusable modules for Databricks workspace, ADLS, Key Vault, networking
  • Module registry — internal module catalogue enforcing approved patterns
  • Terraform plans reviewed as part of PR checks before apply
  • Drift detection: scheduled terraform plan runs detect manual changes
  • State locking prevents concurrent modifications to infrastructure
  • Workspace-per-environment isolation: dev / staging / prod state files separate
  • Provider version pinning: no floating ~> constraints in production modules

Compute Policies
  • Cluster policies defined in Terraform — engineers select from approved policy catalogue
  • Job clusters: auto-terminated after job completion — no idle compute
  • Interactive clusters: auto-termination after 30 min inactivity (configurable)
  • Maximum cluster size caps enforced per environment tier
  • Spot instance ratio ≥ 70% for non-critical batch jobs
  • GPU cluster policies restricted to approved AI/ML workload groups

Cluster Resizing Techniques
  • Autoscaling: min/max worker configuration based on SLA tier — enabled by default
  • Enhanced Autoscaling (EA): Photon-enabled clusters use predictive scale-up
  • Cluster sizing runbook: recommended configurations per workload pattern
  • Instance pool warm nodes for low-latency cluster start on streaming workloads
  • Right-sizing reviews scheduled quarterly — cluster advisor recommendations actioned
  • DBUs/hour tracked per cluster; anomalies flagged to cost dashboard

Compute Optimisation
  • Photon engine enabled for all SQL and ETL clusters — 2-5x performance gains
  • Serverless compute for Databricks SQL Warehouses — auto-scales to zero
  • Workload isolation: streaming, batch, and BI queries on separate cluster pools
  • Delta cache acceleration enabled on data lake clusters
  • Shuffle optimisation: broadcast joins preferred over shuffle joins for small tables
  • Adaptive Query Execution (AQE) enabled globally — dynamic partition coalescing

📋 Ops Readiness Framework
Change management, incident management, compliance auditing, and support processes
Production Readiness Checklist Before any new service or pipeline is promoted to production, it must pass the MRx Ops Readiness Review. This cross-functional review ensures that operational, compliance, and support requirements are met before the system is live.
🔄
Change Management
  • All production changes tracked as Change Requests (CR) in ServiceNow
  • Change classification: Standard (pre-approved), Normal (reviewed), Emergency
  • Normal changes require Change Advisory Board (CAB) approval — meets weekly
  • Change window: production deployments restricted to approved windows
  • Automated CR creation triggered by GitHub Actions on prod deploy pipeline start
  • Post-implementation review (PIR) mandatory for all Normal and Emergency changes
  • Change success rate and MTTR tracked on monthly ops dashboard
ServiceNowCAB
🚨
Incident Management
  • Incidents managed in ServiceNow ITSM with defined priority matrix
  • P1 (Critical): <15 min acknowledge, <1 hr resolve — 24/7 on-call
  • P2 (High): <1 hr acknowledge, <4 hr resolve — business hours on-call
  • P3/P4: <4 hr acknowledge, best-effort resolve — standard support queue
  • PagerDuty escalation policies configured per service tier
  • Incident war room: dedicated Teams channel auto-created for P1 incidents
  • Blameless post-mortems published within 5 business days of P1/P2 closure

💰 Cost Avoidance & FinOps
Cost monitoring, optimisation strategies, and FinOps tooling for sustainable platform economics
FinOps Principles MRx adopts FinOps (Financial Operations) practices to ensure cloud spend is transparent, accountable, and optimised. Every team has visibility into their spending, and cost is treated as a first-class engineering concern — not an afterthought.
📊
Cost Monitoring
  • Azure Cost Management + Billing — primary FinOps tooling for Azure spend
  • Databricks DBU consumption tracked via Databricks Account Console cost view
  • Cost anomaly detection alerts: >20% week-on-week increase triggers review
  • Monthly cost reports distributed to domain leads and platform owner
  • Chargeback model: costs allocated to teams via CostCenter tags
  • Budget alerts at 80% and 100% of monthly target — email + Teams notification
  • FinOps review embedded in monthly ops review meeting agenda
Azure Cost MgmtFinOps
⚡
Cost Avoidance Techniques
  • Spot instances: ≥70% of batch compute on Azure Spot VMs (up to 90% saving)
  • Auto-termination: All interactive clusters terminate after 30 min idle
  • Serverless SQL: Databricks SQL Warehouses scale to zero between queries
  • Dev/staging shutdown: Non-prod environments powered off 22:00–06:00 UTC
  • Data lifecycle: Bronze data lifecycle policies archive to cool storage after 90 days
  • Azure Reserved Instances: 1-year reservations for baseline cluster compute
  • Right-sizing: Cluster advisor recommendations reviewed and actioned quarterly
Spot InstancesServerless
📈
Cost Governance
  • New workloads require cost estimate sign-off before infrastructure provisioning
  • Cost estimates generated from Terraform plan output — reviewed in PR
  • Infracost tool integrated into GitHub Actions to show per-PR cost delta
  • Workload classification: cost tier (Small / Medium / Large) drives compute policy
  • Unused resources audit monthly: orphaned disks, stopped VMs, idle gateways
  • FinOps maturity targets: Crawl → Walk → Run model with quarterly assessment

📡 Platform Observability
Grafana dashboards, Azure Monitor alerting, and end-to-end platform health visibility
Observability Stack The MRx observability stack is built on Azure Monitor (metrics and logs) and Grafana (visualisation and alerting), providing a unified view of platform health from infrastructure uptime through to data pipeline SLA compliance.
📊
Grafana Dashboards
  • Platform Health Dashboard: Cluster uptime, job success rate, API latency, storage capacity
  • Pipeline SLA Dashboard: Per-pipeline SLA compliance (target latency vs actual)
  • Data Quality Dashboard: DQ rule pass/fail rates, anomaly trend over time
  • Cost Dashboard: DBU consumption, Azure spend, cost-per-pipeline metrics
  • Security Dashboard: Security alert trend, open findings by severity, compliance posture
  • Incident Dashboard: Open incidents by priority, MTTR trends, escalation rates
  • All dashboards version-controlled as JSON in grafana/dashboards/ Git repo
  • Grafana provisioned and configured via Terraform (Grafana provider)
GrafanaDashboardsGitOps
🔔
Azure Monitor
  • Log Analytics Workspace: Central log aggregation from all Azure services and Databricks
  • Diagnostic settings enabled on all resources — logs streamed to Log Analytics
  • Alert rules: KQL queries detecting anomalies in metrics and log data
  • Action groups: email, Teams webhook, PagerDuty, and ServiceNow for escalation
  • Application Insights: APM for any REST APIs deployed alongside pipelines
  • Custom metrics published from Databricks jobs via Azure Monitor REST API
  • Workbooks for ad-hoc investigation and root cause analysis
  • Metric alerts: CPU, memory, storage SAS token expiry, Key Vault access failures
