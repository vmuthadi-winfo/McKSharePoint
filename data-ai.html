🗄️ Pillar 3 — Data Management
Modeling standards, catalog structure, medallion architecture, and storage optimization
Medallion Architecture The CoE mandates the Medallion architecture pattern for all MRx data assets — a multi-layer strategy that incrementally improves data quality and structure as data flows from raw ingestion (Bronze) through cleansed (Silver) to business-ready (Gold).
🟤
BRONZE — Raw Zone

Exact copy of source data. No transformations. Immutable append-only Delta tables. Full history retained.

  • Schema-on-read with Autoloader schema inference
  • Partition by ingest_date for efficient pruning
  • 30-day retention for raw streams; 7-year for compliance datasets
  • No PII masking at this layer — access restricted
⚪
SILVER — Conformed Zone

Cleansed, deduplicated, typed, and enriched. Business rules applied. Standardized schema and naming.

  • Data quality checks applied (nulls, ranges, referential integrity)
  • SCD Type 2 patterns for slowly-changing dimensions
  • PII tokenisation and masking applied at this layer
  • Z-ordering on high-cardinality filter columns
🟡
GOLD — Business Zone

Aggregated, business-specific datasets. Dimensional models and KPIs ready for analytics and ML consumption.

  • Optimised for read performance (BI tools, SQL analytics)
  • Governed via Unity Catalog with row/column-level security
  • Published to Alation for self-service data discovery
  • Every column mapped to business glossary term
📐
Data Modeling
  • Dimensional and Data Vault 2.0 patterns supported
  • Entity-relationship docs required for all new domains
  • Schema changes governed via CoE change control process
  • Naming convention: snake_case, domain-prefixed (e.g., mrx_customer_id)
  • Surrogate keys generated via hash (md5/sha256)
📚
Data Catalog Structure
  • Unity Catalog hierarchy: metastore → catalog → schema → table
  • Naming conventions enforced by CI validation
  • All production tables: managed Delta tables in Unity Catalog
  • External tables require CoE approval
  • Table documentation: owner, classification, PII flag, retention policy
Unity CatalogManaged Tables
🧹
Partitioning & Vacuuming
  • Partition columns: date/event_date for time-series; geography or business key for large reference datasets
  • OPTIMIZE: scheduled weekly — compacts small files to 128 MB targets
  • VACUUM: 7-day default retention; 30-day for regulated datasets
  • Delta table statistics collected automatically for query plan optimisation
  • Liquid clustering evaluated for high-churn tables
OPTIMIZEVACUUMDelta Lake

🚨 Pillar 5 — Error Handling Framework
Audit logs, exception management, alerting, and operational visibility
📋
Audit Logs
  • All pipeline executions logged: start/end time, record counts, schema, user, job ID
  • Stored in Unity Catalog audit schema — immutable append-only Delta table
  • Retention: 90 days operational; 7 years for SOX compliance datasets
  • Accessible via Databricks SQL and Grafana audit dashboard
⚠️
Exception Logs
  • Structured exception capture: error type, severity, affected records, stack trace
  • Written to dedicated exception Delta table per pipeline
  • Dead-letter tables for unresolvable records — quarantined for investigation
  • Retention: 180 days
  • Exception records linked to source row identifier for lineage tracing
📣
Alerting Framework
  • Azure Monitor + Grafana alerts with configurable thresholds
  • Alert triggers: p99 latency, failure rate, row count anomaly, DQ score drop
  • Routed to Slack, email, and PagerDuty by severity
  • Automated error reports generated daily for critical failures
  • SLA breaches escalated to team lead automatically
Azure MonitorPagerDutyGrafana
🔍
Root Cause Tooling
  • Grafana for log correlation across Databricks, ADF, and storage
  • Azure Application Insights for distributed tracing with correlation IDs propagated through all pipeline hops
  • End-to-end visibility from data source through to Gold layer output
🔁
Retry Policies & Alert Severity
  • Configurable retry with exponential backoff — max 3 retries for transient failures
  • P1: Pipeline down >15 min → immediate PagerDuty page
  • P2: DQ failure → team lead notification
  • P3: Latency breach → email alert
  • P4: Warning → Slack channel notification
🔄 Pillar 6 — CI/CD Framework
Automated delivery, release management, and deployment governance
GitOps Model All MRx platform changes follow a GitOps model — the Git repository is the single source of truth for both application code and infrastructure configuration. Deployments are triggered exclusively through GitHub Actions / Azure Pipelines with mandatory approval gates.
📦
Databricks Asset Bundles
  • DABs package jobs, workflows, notebooks, and DLT pipelines as a single deployable unit
  • Bundle definitions in databricks.yml — versioned alongside code
  • Environment targets: dev → staging → prod with variable overrides
  • Bundle validation in PR checks before merge
  • Rollback via previous bundle version re-deployment
DABGitOps
🗂️
Git Repository Strategy
  • Branch strategy: main → release → feature (trunk-based development)
  • PR required for all changes — auto-merge blocked without approvals
  • Signed commits enforced for merges to main
  • Semantic versioning (vMAJOR.MINOR.PATCH) for all release tags
  • Azure DevOps / GitHub — repo settings enforced via Terraform
GitHubTrunk-Based
