🗄️ Data Management
Data architecture, catalog structure, storage patterns, and table management
Medallion Architecture The MRx platform implements the Medallion architecture pattern — a multi-layer data organisation strategy that incrementally improves data quality and structure as data flows from raw ingestion (Bronze) through cleansed/conformed (Silver) to business-ready aggregations (Gold).
🥉
Bronze Layer — Raw Ingestion

Purpose: Exact replica of source data — no transformations

  • Raw files / events stored as-is (JSON, CSV, Parquet)
  • Schema-on-read with Auto Loader schema inference
  • Append-only Delta tables with ingestion metadata columns
  • Partition by: ingest_date for efficient pruning
  • 30-day retention policy for raw streams; 7-year for compliance datasets
  • No PII masking at this layer (access restricted)
🥈
Silver Layer — Cleansed & Conformed

Purpose: Validated, deduplicated, type-cast data ready for analytics

  • Schema enforcement with explicit column definitions
  • Data quality checks applied (nulls, ranges, referential integrity)
  • SCD Type 2 patterns for slowly-changing dimensions
  • PII tokenisation and masking applied at this layer
  • Partition by: entity_date or business key ranges
  • Z-ordering on high-cardinality filter columns for query acceleration
🥇
Gold Layer — Business-Ready

Purpose: Aggregated, business-domain-aligned datasets for BI and ML

  • Fact tables, wide denormalised tables, and pre-aggregated metrics
  • Optimised for read performance (BI tools, SQL analytics)
  • Business glossary terms applied to column names and descriptions
  • Governed via Unity Catalog with row/column-level security
  • Published to Alation for self-service data discovery
  • API-accessible via Databricks SQL endpoints
🗂️
Data Modelling Standards
  • Logical modelling: Entity-Relationship diagrams maintained in LucidChart / draw.io
  • Physical modelling: Column-level data types, constraints, and default values in code
  • Naming conventions: snake_case, domain-prefixed (e.g., mrx_customer_id)
  • All tables require: primary key definition, owner tag, classification label
  • Surrogate keys generated via hash (md5 / sha256) for consistency
  • Model versioning: DDL migrations tracked in Liquibase-style changelog
🔧
Managed Tables: Partitioning & Vacuuming
  • Partitioning strategy: Date-based (daily) for time-series; range-based for large lookups
  • Partition column guidelines: cardinality < 10,000 distinct values recommended
  • OPTIMIZE: Scheduled weekly to compact small files into 128 MB targets
  • VACUUM: Scheduled weekly with 7-day retention threshold minimum
  • Delta table statistics collected automatically for query plan optimisation
  • Liquid clustering evaluated for high-churn tables replacing static partitions

🧪 Testing Framework
Data quality checks, unit testing, and validation patterns across the platform
✅
Data Quality Framework

MRx implements a declarative DQ framework applied at the Silver and Gold layers, with quality metrics persisted for auditing.

  • Completeness checks: Null/empty rate per critical column below threshold
  • Uniqueness checks: Duplicate detection on primary/business keys
  • Range/domain checks: Value within expected enumeration or numeric range
  • Referential integrity: Foreign key lookups against reference tables
  • Timeliness checks: Data freshness SLA enforcement (lag < N hours)
  • Volume anomaly detection: Record count deviates > 3σ from historical baseline
  • DQ results written to audit.dq_results table for dashboarding in Grafana
  • Pipeline fails on critical DQ rule violation; warns on soft rules
Great ExpectationsDLT Expectations
🔬
Unit Testing Framework

All transformation logic is unit-tested using Python testing frameworks integrated into the CICD pipeline.

  • pytest — primary unit testing framework for Python transformation functions
  • chispa — PySpark DataFrame assertion library for Spark unit tests
  • Test data fixtures managed as small Parquet snapshots in tests/fixtures/
  • Mocking of Databricks context via unittest.mock for local test execution
  • Code coverage ≥80% enforced by SonarQube quality gate
  • Tests run in isolated Databricks test cluster via GitHub Actions
  • Parallel test execution to minimise CI pipeline duration
  • Regression test suite run against prod data snapshots pre-deployment

🚨 Error Handling & Audit Framework
Comprehensive logging, exception management, and alerting across all MRx pipelines
📖
Audit Logs
  • Centralised audit log table: audit.pipeline_audit_log
  • Captures: job_id, run_id, source, target, start/end time, rows written, status
  • Immutable append-only Delta table (no UPDATE / DELETE allowed)
  • Audit log entries required for SOX/SOC compliance controls
  • Retention: 7 years for compliance datasets; 90 days for operational logs
  • Accessible via Databricks SQL and Grafana audit dashboard
⚠️
Exception Logging
  • Structured exception logging using Python logging with JSON formatter
  • Exception table: audit.exception_log with full stack trace and context
  • Severity levels: DEBUG / INFO / WARN / ERROR / CRITICAL
  • Dead-letter queue for records failing transformation — quarantined for investigation
  • Exception records linked to source row identifier for lineage tracing
  • Exceptions surfaced in Databricks notebook output and Azure Monitor
📣
Error Reporting & Alerting
  • Azure Monitor Alert Rules trigger on pipeline failure events
  • PagerDuty integration for critical pipeline failures (P1/P2)
  • Email/Teams notifications for P3/P4 failures via Logic App
  • Grafana alert panels show real-time error rates and SLA breach risk
  • Runbook links embedded in alert notifications for rapid response
  • Alert deduplication and suppression to prevent notification storms

🔄 CICD Pipeline
Release management, deployment automation, and feature flag controls
GitOps Model All MRx platform changes follow a GitOps model — the Git repository is the single source of truth for both application code and infrastructure configuration. Deployments are triggered exclusively through GitHub Actions pipelines with mandatory approval gates.
📦
Databricks Asset Bundles
  • Asset Bundles (DAB) package jobs, notebooks, and DLT pipelines as a single deployable unit
  • Bundle definitions in databricks.yml — version-controlled alongside code
  • Environment targets: dev → staging → prod with variable overrides
  • Bundle validation run as part of PR checks before merge
  • databricks bundle deploy triggered by GitHub Actions on release
  • Rollback via previous bundle version re-deployment (no manual state manipulation)
Asset BundlesGitOps
⚡
GitHub Actions Workflows
  • PR Workflow: lint → test → SonarQube → bundle validate → security scan
  • Deploy to Dev: Triggered on merge to develop branch — fully automated
  • Deploy to Staging: Triggered on merge to release/* — automated with smoke tests
  • Deploy to Prod: Manual approval gate required (Tech Lead + Product Owner)
  • Workflow templates in .github/workflows/ reused across all MRx repositories
  • Secrets managed via GitHub Actions Secrets and Azure Key Vault
GitHub ActionsAutomation
🚩
Feature Flags
  • Feature flags enable safe incremental rollout of new pipeline features
  • Flags stored in Azure App Configuration — no code deployment needed to toggle
  • Flag scopes: user, environment, percentage rollout
  • Kill-switch flags for instant feature disablement in production incidents
  • Flag lifecycle managed: Temporary (for gradual rollout) vs Permanent (ops control)
  • Stale flags cleaned up quarterly to prevent configuration drift
Feature FlagsApp Config
🔐
Approval Gateway & Release Management
  • All production deployments require minimum 2 approvals from authorised gatekeepers
  • Approval matrix: Tech Lead (mandatory) + Product Owner or Release Manager
  • GitHub Environments with required reviewers enforce the approval workflow
  • Change record automatically created in ServiceNow on prod deployment trigger
  • Deployment window enforcement: no prod deployments on Fridays or peak hours
  • Post-deployment smoke tests must pass before approval ticket closed
